## 一、背景

当前仓库是一套成熟的 HTML5 魔塔引擎 + 可视化编辑器：

- `libs/` + `main.js` 约 2.37 万行，`_server/`（编辑器）约 2.42 万行，全部为手写 ES5 代码。
- 无 `package.json`，无构建、无 lint、无测试。
- 模块以全局变量 + `<script>` 按 `main.loadList` 固定顺序动态加载；`core` 是全局单例，依赖 `eval` 把各子模块方法转发到 `core` 上。
- 用户塔数据 `project/*.js` 是带硬编码 GUID 后缀的全局变量，由编辑器用特殊 replacer 的 `JSON.stringify` 写回。
- 服务端为原生 node（`server.js`）与 Flask（`server.py`），仅用于托管资源与提供编辑器文件读写接口。

多年迭代积累了大量边界处理逻辑（临界值计算、录像序列化/回放、地图 id 映射、UI 高清化取整、平台差异等），这是最有价值也最容易被重写丢失的部分。

## 二、目标与决策

本次改造为**全项目重写**，已确定：

| 决策项 | 结论 |
| --- | --- |
| 兼容性 | 不要求兼容旧 API / 旧全局变量 / 旧数据格式 |
| 数据格式 | 全新格式，另写迁移器转换旧塔 |
| 技术栈 | 全面 TypeScript（strict） |
| 范围 | 引擎 + 编辑器 + 服务端 + 构建发布，整体重写 |
| 运行形态 | 统一 bun 服务 |
| 包管理 | pnpm |
| 运行时 / 构建 / 测试 / 服务 | bun |

## 三、技术栈

| 领域 | 选型 |
| --- | --- |
| 包管理 | pnpm |
| 运行时 / 构建 / 测试 / 服务 | bun（`Bun.serve`、`bun build`、`bun test`） |
| 语言 | TypeScript（strict，原生 JSX） |
| 运行时数据校验 | zod / valibot |
| 静态检查 | tsc --noEmit |
| Lint / 格式化 | ESLint（typescript-eslint）+ Prettier，`.prettierignore` 不再忽略 `*.js` |
| 游戏渲染 | Canvas 2D（保留），可选 OffscreenCanvas 增强 |
| 游戏 UI 层 | DOM + Preact + `@preact/signals`（详见「六、UI 层方案」） |

## 四、总体策略

全量重写最大的风险不是写不出来，而是丢掉成熟引擎里那些不起眼的边界处理。因此采用**绞杀者模式（Strangler Fig）+ 新骨架**：

> 新架构、新工具链、新数据格式，但业务逻辑按模块从旧代码**有测试地迁移和重写**，而不是凭记忆从零手撸。每个模块行为对齐后再替换，最后删除旧代码。

这样既得到干净的 TS 架构，又不会把踩过的坑再踩一遍。

## 六、UI 层方案

UI 层按更新频率与可定制性拆成三层，不用一个框架通吃：

| 类别 | 内容 | 更新频率 | 实现 |
| --- | --- | --- | --- |
| A 地图渲染 | 层、图块、勇士、动画帧 | 每帧 | Canvas 2D（`#game`） |
| B 特效层 | 光标、箭头、显伤、`effect`、塔作者 ui 事件绘制 | 每帧 | Canvas 叠加层（`#fx`，`pointer-events: none`） |
| C HUD / 面板 | 状态栏、对话框/选项/确认/输入、tip、道具箱、装备、怪物手册、楼层传送、存读档、设置、统计、帮助、商店、虚拟键盘 | 事件驱动 | DOM（`#ui`）+ Preact |
| D 主题皮肤 | 九宫格窗口皮肤、配色、字体、图标、排版 | 开局一次 | CSS 变量 + `border-image` |

> 旧引擎本就是「DOM 状态栏 + canvas 地图/面板」的混合体（`index.html` 的 `#statusBar`、`project/functions.js` 里的 `core.statusBar.atk.innerText`）。本次不是「canvas 转 DOM」，而是重新划定 B/C 的边界：原先画在 canvas 上的面板（`drawBook`/`_drawToolbox`/`_drawEquipbox`/`drawFly`/`_drawSLPanel`/`_drawSettings`/`_drawStatistics`…）搬到 C，原先每帧刷 canvas 的留在 A/B。

### 选型

DOM 层用 **Preact + `@preact/signals`**：

- signals 只更新绑定了它的节点，不需要手工 signature diff，也不做每帧 vdom diff——正好替代 `main.ts` 里「每帧 `renderStatus()` + JSON 签名比对」的临时方案；
- 体积约 5KB gzip，静态导出与移动端友好；
- `tsconfig` 加 `"jsx": "react-jsx"` + `"jsxImportSource": "preact"`，bun 的 HTML import / `bun build` 直接吃 `.tsx`，无需额外插件；
- 同一套设计系统（`src/ui/`）供游戏端与编辑器复用，阶段 6 不必换心智；Monaco / CodeMirror 作为命令式组件用 ref 包一层。

不选 React（体积与静态导出不划算）、Svelte/Solid（需额外编译插件或 props 语义有坑）、Lit（模板与 TS/JSX 生态脱节，shadow DOM 与塔作者主题冲突）、纯 vanilla（游戏端可行，但 20+ 个同构面板与编辑器会写爆样板）。

### 接口与状态流

引擎侧只保留可单测的纯模型，不引入框架依赖：

- `src/engine/modules/ui.ts` 继续只放 `parseRichText` / `formatStatusBar` / `formatMonsterManual` / `DialogController` / `AnimateClock`，通过 `DialogView` / `EventPresenter` 抽象对外；
- 框架只出现在 app 层。引擎变更 → presenter / `UiStore` 写 signal → 仅重渲染订阅节点；
- **帧级数据（勇士位置、动画帧、显伤）不写进 signal**，直接走 `#fx` canvas，避免每帧 DOM 写。

### 外观与扩展点

- 窗口皮肤：旧的 `drawWindowSkin(background, ..., direction, px, py)` 即九宫格，映射为 CSS `border-image-source` / `border-image-slice` / `border-image-repeat`，配 `image-rendering: pixelated`；
- 富文本：`RichText` 组件直接消费已有的 `RichNode[]`（`\i[]` 用 `<img>`），不再需要「逐字画到临时 canvas」；
- 打字机：`signal(revealedChars)` + 已有 `sliceRichText`，定时器归 `AnimateClock`；
- 移动端：`_drawKeyBoard` 变为普通组件，手势用 `#ui` 上的 pointer events；
- 塔作者定制：沿用「数据 + TS 脚本、不要 `eval`」的方针——声明式部分（状态栏槽位、主题、面板定义）走 schema，要自由绘制就调受控的 canvas draw API 画在 `#fx`；旧的 `functions.ui` 直接操作 DOM 的写法没有自动等价物，交给迁移器出「需人工迁移」报告（同道具的 `*Legacy`）。

### 落地顺序

1. ✅ 阶段 5 垂直切片：`main.tsx` 的状态栏 / 对话框 / 面板已换成 `src/ui` + Preact，signals 更新与主题链路已验证（`tests/game-ui.test.ts` 覆盖 signal 对话框与主题）；
2. ✅ 面板按同构程度批量迁移：道具箱/装备（`MotaItems` 已具备全部操作）→ 楼层传送/地图浏览 → 存读档/设置 → 统计/帮助；
3. 阶段 6 直接复用 `src/ui/`，表格用 signals 行级更新或自研虚拟化，不引重型表格库；
4. UI 只呈现，不参与录像/存档一致性校验。

## 七、新数据格式与迁移器

旧格式 `var data_<GUID> = {...}` + 手写 replacer + GUID 全局名，是编辑器复杂度的根源。新方案：

- `project/tower.json`：原 `data.js` 的 `main` 等内容。
- `project/floors/<id>.json`：每层一个文件，无需 `__all_floors__.js` 拼接。
- `project/{enemys,items,maps,events,plugins}.json`。
- 用户脚本 `functions` / `plugins` 改为 `.ts` 模块，通过注入的 API 调用。
- 编辑器使用同一份 schema 生成表格与校验，去掉特殊 `JSON.stringify` replacer。

**迁移器** `scripts/migrate.ts`：

1. 解析旧 JS（`new Function` 提取 GUID 变量）；
2. 转换为 JSON；
3. 按 schema 校验；
4. 输出到新目录结构。

迁移器需配 golden 测试，保证可重复、可验证。

## 八、统一 bun 服务

一个 bun 进程同时提供游戏、编辑器与文件读写 API，替换 `server.js` + `server.py` + `启动服务.exe`：

```ts
import index from "../src/game/index.html";
import editor from "../src/editor/editor.html";

Bun.serve({
  routes: {
    "/": index,
    "/editor": editor,
    "/api/fs/:op": { POST: handleFs },   // read / write / list
    "/api/floors": { GET: listFloors },
  },
  development: { hmr: true },            // 开发时热更新
});
```

- 开发时启用 HMR；生产时托管 `bun build` 产物。
- 文件 API 做路径校验，限制在 `project/` 内。

## 十、待定设计点

1. **塔作者脚本 API**：新引擎不再有全局 `core`，用户脚本采用何种形态（import 模块 / 注入 `api` 对象）？这是对外契约，需尽早确定。
2. **编辑器图块系统**：继续使用 Blockly，还是按 `_server/refactoring.md` 做自研简洁图块系统。
3. **资源组织**：`project/assets/` 的图片 / 音频是否保持原文件名（迁移器需处理），还是重新组织。
4. **旧塔迁移范围**：迁移器需兼容到多旧版本（仅当前 2.10.x，还是更早）。
5. **静态导出**：统一 bun 服务之外，是否需要「导出静态站点」能力，让玩家无需 bun 也能游玩。
6. **窗口皮肤的逃生通道**：RM 布局的 `winskin.png`（192x128，背景贴 `(0,0,128,128)`、边条在 `x=144` / `y=48`）已在加载时用 canvas 重切成标准 48x48 九宫格交给 `border-image`（`src/game/skin.ts`），不再需要 canvas underlay；若遇到非规则边框 / 自定义拉伸区的皮肤，仍保留「canvas underlay 画皮肤、DOM 只放内容」的备用路径。

## 十一、风险与建议

- **风险**：全量重写易丢失成熟边界逻辑；UI / 录像 / 存档等回归成本高。塔作者自定义 UI 与极端窗口皮肤在 DOM/CSS 下无自动等价物，还原度依赖人工迁移。
- **对策**：绞杀者模式 + 纯逻辑单元测试 + 逐模块对照验收。保留 `#fx` canvas 特效层与「canvas underlay 画皮肤」逃生通道；自定义 UI 提供「`firstData.ui` 数据 + `mota.ui.register` 数据钩子」两级等价物（阶段 5 已落地，见「阶段 5 已完成」），迁移器对自定义 UI 出具人工迁移报告。
- **建议起点**：先做阶段 0 + 1。风险低、成果明确，迁移器跑通即证明新数据格式可行，并解锁后续工作。
- **首个里程碑**：阶段 3 的最小可玩闭环。跑通后其余即规模化生产。
